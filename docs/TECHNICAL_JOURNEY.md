## 1. 프로젝트 개요

### 1.1 무엇을 만드는가?

**CatTalk2D** = 고양이 시뮬레이션 게임 + AI 대화 시스템

```
┌─────────────────────────────────────────────────┐
│  플레이어가 고양이 "망고"를 키운다              │
│                                                 │
│  - 밥을 주고                                    │
│  - 쓰다듬고                                     │
│  - 대화하고                                     │
│  - 시간이 흐르면서 고양이가 성장               │
│                                                 │
│  핵심: 고양이가 "진짜 고양이처럼" 반응해야 함   │
└─────────────────────────────────────────────────┘
```

### 1.2 핵심 목표

| 목표 | 설명 |
|------|------|
| **고양이다움** | 츤데레, 변덕, 행동 묘사 등 실제 고양이 같은 반응 |
| **상태 반영** | 배고프면 밥 달라고, 피곤하면 졸린 반응 |
| **신뢰도 반영** | 처음엔 경계, 친해지면 애교 |
| **로컬 실행** | 인터넷 없이도 동작 |

## 2. 왜 로컬 LLM인가?

### 2.1 선택지들

| 방식 | 장점 | 단점 |
|------|------|------|
| **ChatGPT API** | 품질 최고 | 비용 발생, 인터넷 필수, 레이턴시 |
| **규칙 기반** | 빠름, 예측 가능 | 다양성 없음, 하드코딩 지옥 |
| **로컬 LLM** | 무료, 오프라인, 커스텀 가능 | 품질 낮음, 설정 복잡 |

### 2.2 로컬 LLM을 선택한 이유

```
1. 비용 문제
   - ChatGPT API: 1000번 호출 ≈ $1~5
   - 게임에서 대화 수천번 → 비용 감당 불가

2. 레이턴시 문제
   - 인터넷 왕복: 500ms~2초
   - 로컬: 100ms~500ms
   - 게임에서 체감 차이 큼

3. 커스터마이징
   - 로컬 모델은 LoRA로 "고양이다움"을 직접 학습 가능
   - API는 프롬프트 엔지니어링에만 의존

4. 오프라인 지원
   - 인터넷 없어도 게임 플레이 가능
```

### 2.3 로컬 LLM의 한계 인정

```
문제: 로컬 모델은 GPT-4보다 "멍청함"
      - 지시 무시 빈번
      - 영어로 대답
      - 고양이답지 않은 응답

해결책:
1. 프롬프트 강화 → Control 시스템
2. 후처리 → ResponseProcessor
3. 직접 학습 → LoRA
```

## 3. 왜 Ollama인가?

### 3.1 로컬 LLM 실행 방법들

| 방법 | 복잡도 | 성능 | 사용성 |
|------|--------|------|--------|
| **PyTorch 직접** | 매우 높음 | 최고 | 개발자만 가능 |
| **llama.cpp** | 높음 | 좋음 | CLI 필요 |
| **LM Studio** | 낮음 | 보통 | GUI, 무거움 |
| **Ollama** | 매우 낮음 | 좋음 | REST API, 가벼움 |

### 3.2 Ollama 선택 이유

```
1. 설치 간단
   - 설치 파일 하나로 끝
   - 모델 다운로드: ollama pull qwen2.5:3b

2. REST API 제공
   POST http://localhost:11434/api/generate
   → Unity에서 UnityWebRequest로 바로 호출 가능

3. 모델 관리 쉬움
   - ollama list: 설치된 모델 목록
   - ollama rm: 모델 삭제
   - ollama create: 커스텀 모델 생성

4. GGUF 지원
   - 양자화된 가벼운 모델 사용 가능
   - 일반 PC에서도 실행 가능
```

### 3.3 Ollama가 내부적으로 하는 일

```
┌────────────────────────────────────────────────┐
│  사용자: ollama run qwen2.5:3b                 │
│                                                │
│  내부 동작:                                     │
│  1. ~/.ollama/models/에서 모델 파일 로드       │
│  2. llama.cpp 엔진으로 추론 실행               │
│  3. GPU 있으면 자동으로 GPU 사용               │
│  4. REST API 서버 실행 (localhost:11434)       │
└────────────────────────────────────────────────┘
```

## 4. 고양이다움을 어떻게 만들 것인가?

### 4.1 초기 접근: 프롬프트만으로

```
시도 1: 간단한 프롬프트
─────────────────────────
"너는 고양이야. 고양이처럼 대답해."

결과: "안녕하세요, 무엇을 도와드릴까요?"
     → 완전히 실패. 고양이 같지 않음.
```

```
시도 2: 상세한 프롬프트
─────────────────────────
"너는 '망고'라는 이름의 고양이다.
 성격은 츤데레이고, 문장 끝에 '냥'을 붙인다.
 1-2문장으로 짧게 대답한다."

결과: "안녕하냥! 뭐가 필요하냥?"
     → 조금 나아졌지만, 여전히 문제:
        - 행동 묘사 없음
        - 상태(배고픔, 피곤함) 반영 안됨
        - 신뢰도 반영 안됨
```

### 4.2 문제 인식

```
문제들:
1. 모델이 "지금 배고프다"는 정보를 모름
2. 모델이 "나를 얼마나 좋아하는지" 모름
3. 모델이 "지금 몇 시인지" 모름
4. 모델이 "어떤 행동을 해야 하는지" 판단 못함

→ 게임 상태를 모델에게 전달해야 함
→ Control 시스템 탄생
```

### 4.3 Control 시스템 설계

```
핵심 아이디어:
─────────────
게임의 모든 상태를 JSON으로 정리해서 프롬프트에 포함

[현재 상태]
- 나이: 아기 고양이 (활발하고 귀여운 말투)
- 현재 기분: 배고픔 (밥에 관심)
- 주인과의 관계: 높음 (애정 표현 많음)

→ 모델이 "지금 배고프고, 나를 좋아하는 아기 고양이"로 연기
```

## 5. Control 기반 시스템 설계

### 5.1 CatState (게임 상태)

```csharp
// 게임에서 추적하는 고양이 상태
public class CatState
{
    // 기본 상태 (0~100)
    public float Hunger;      // 배고픔 (높을수록 배고픔)
    public float Energy;      // 에너지 (낮을수록 피곤)
    public float Stress;      // 스트레스
    public float Fun;         // 재미/만족도
    public float Affection;   // 호감도
    public float Trust;       // 신뢰도 (친밀감)

    // 나이
    public int AgeDays;       // 생후 일수

    // 성격 (고정값)
    public float Playful;     // 장난기
    public float Shy;         // 소심함
    public float Aggressive;  // 까칠함
    public float Curious;     // 호기심
}
```

### 5.2 CatState → Control 변환

```
게임 상태를 AI가 이해할 수 있는 형태로 변환

CatState                          Control
─────────                         ───────
trust: 75       ──────────→      trustTier: "high"
hunger: 80      ──────────→      needTop1: "food"
energy: 30      ──────────→      moodTag: "tired"
ageDays: 30     ──────────→      ageLevel: "child"
현재시간 14:00  ──────────→      timeBlock: "afternoon"
```

### 5.3 TrustTier 결정 로직

```
왜 TrustTier가 중요한가?
────────────────────────
실제 고양이도 처음 보는 사람에게는 경계하고,
친한 사람에게는 애교를 부린다.

이걸 구현하려면:
- trust가 낮으면: "하악!", "가까이 오지마"
- trust가 높으면: "골골~", "좋아!"

TrustTier 기준:
- LOW (0~30):   경계, 거리두기
- MID (31~70):  츤데레, 중립
- HIGH (71~100): 친밀, 애착
```

### 5.4 실제 프롬프트 예시

```
[현재 상태]
- 나이: 아기 고양이 (활발하고 귀여운 말투, '~', '!' 자주 사용)
- 현재 기분: 배고픔 (밥에 관심, 간식 원함)
- 주인과의 관계: 주인을 매우 좋아함 (애정 표현 많음)

[응답 규칙]
1. 현재 기분과 나이에 맞는 말투를 사용해
2. 주인과의 관계(호감도)에 맞게 반응해
3. 반드시 행동 묘사를 (괄호) 안에 포함해 (예: 골골, 하품, 꼬리 흔들기)
4. 짧고 직설적으로 1~2문장만 답해
```

## 6. 벤치마크 시스템 탄생

### 6.1 왜 벤치마크가 필요한가?

```
문제:
─────
"이 모델이 저 모델보다 나은 것 같아"
→ "같아"가 아니라 "수치로" 비교해야 함

예시:
- gemma2:2b vs qwen2.5:3b
- 어느 게 더 "고양이다운" 응답을 하는가?
- 감으로 판단? → 객관성 없음
```

### 6.2 평가 기준 설계

```
BasicScore (25점 만점)
──────────────────────
1. Control 준수율 (5점): 지시를 따르는가?
2. 상태 반영률 (5점): 배고프면 밥 얘기 하는가?
3. 나이 말투 (5점): 아기면 아기답게, 어른이면 어른답게
4. 호감도 태도 (5점): 신뢰 낮으면 경계, 높으면 친밀
5. 행동묘사/표현 (5점): (괄호) 안에 행동 표현 있는가?
```

### 6.3 CatLikenessScore 상세

```
키워드 기반 채점
────────────────
응답에 특정 키워드가 있으면 점수 부여

예시:
"(하품) 졸려... 귀찮아."
   ↓
- Action 점수: (하품) 있음 → +10점
- Routine 점수: "졸려" 포함 → +8점
- Tsundere 점수: "귀찮아" 포함 → +5점
```

### 6.4 벤치마크 결과 예시 (실제 데이터)

```
=== cattalk-20260125 벤치마크 결과 ===

[세부 점수]
- Control 준수율: 1.1/5
- 상태 반영률: 1.3/5
- 나이 말투 일치: 1.6/5
- 호감도 태도 일치: 2.7/5
- 행동묘사/표현: 3.7/5

=== qwen2.5:3b 벤치마크 결과 ===
총점: 14.5/25 (C등급)

[세부 점수]
- Control 준수율: 2.0/5
- 상태 반영률: 2.8/5
- 나이 말투 일치: 2.7/5
- 호감도 태도 일치: 2.5/5
- 행동묘사/표현: 4.5/5
```

## 7. LoRA 학습 결정 과정

### 7.1 왜 LoRA인가?

```
선택지:
1. Full Fine-tuning: 모델 전체 재학습
   - 장점: 최고 품질
   - 단점: 수십GB VRAM 필요, 수일 소요

2. LoRA (Low-Rank Adaptation): 일부만 학습
   - 장점: 8~12GB VRAM OK, 1시간 내 학습
   - 단점: Full보다 약간 품질 낮음

3. 프롬프트만: 학습 없이 프롬프트 개선
   - 장점: 즉시 적용
   - 단점: 한계 있음

결론: LoRA 선택
- 로컬 RTX 3060 (12GB)에서 실행 가능
- 충분한 품질 개선 기대
```

### 7.2 LoRA가 뭔가? (쉬운 설명)

```
원래 모델 학습:
──────────────
모델 전체 파라미터 수정 = 수십억 개 숫자 변경
→ 시간 오래, 메모리 많이 필요

LoRA 학습:
──────────
모델은 그대로, 작은 "패치"만 학습
→ 수백만 개 숫자만 변경
→ 빠르고 가벼움

비유:
- Full: 책 전체를 새로 쓰기
- LoRA: 책에 포스트잇으로 수정사항만 붙이기
```

### 7.3 학습 데이터 생성

```
어떤 데이터가 필요한가?
────────────────────────
{
  "messages": [
    {"role": "system", "content": "[현재 상태] 아기 고양이, 배고픔..."},
    {"role": "user", "content": "안녕?"},
    {"role": "assistant", "content": "(꼬리 흔들며) 왔다! 밥 줘!"}
  ]
}

→ "이런 상황에서 이렇게 대답해"를 수백~수천 개 만들어서 학습
```

### 7.4 베이스 모델 선택

```
후보:
1. polyglot-ko-1.3B: 한국어 전용, 가벼움
2. Qwen2.5-1.5B: 다국어, 품질 좋음
3. Gemma2-2B: 구글, 균형 잡힘

테스트 결과:
- Qwen2.5가 한국어 품질 가장 좋음
- GGUF 변환 지원됨
→ Qwen2.5 선택
```

## 8. 위기와 해결

### 8.1 위기 1: 학습 모델이 베이스보다 점수 낮음

```
상황:
──────
LoRA 학습 후 벤치마크 실행
→ cattalk-20260125: 10.4점
→ qwen2.5:3b (베이스): 14.5점

"학습했는데 오히려 점수가 낮아졌다?!"
```

```
원인 분석:
──────────
학습 데이터 형식:
  [CONTROL]{"trustTier":"high",...}
  [USER]안녕?

벤치마크 프롬프트 형식:
  [현재 상태]
  - 나이: 아기 고양이
  - 기분: 배고픔

→ 형식이 완전히 다름!
→ 모델이 학습한 형식과 테스트 형식이 불일치
```

```
해결:
──────
학습 데이터 형식을 벤치마크와 동일하게 변경

[현재 상태]
- 나이: 아기 고양이 (활발하고 귀여운 말투)
- 현재 기분: 배고픔
- 주인과의 관계: 높음

[응답 규칙]
1. 기분에 맞게 반응
2. 행동 묘사 필수
...
```

### 8.2 위기 2: GGUF 변환 실패

```
상황:
──────
LoRA 학습 완료
→ GGUF 변환 시도
→ "지원되지 않는 모델 아키텍처" 에러
```

```
원인:
──────
베이스 모델 선택 실수
- polyglot-ko: GGUF 변환 지원 안됨
- Qwen2.5: 지원됨

일부 오래된 모델은 llama.cpp에서 지원 안함
```

```
해결:
──────
1. 베이스 모델 교체 (polyglot → Qwen2.5)
2. 모델 선택 시 GGUF 지원 여부 확인 필수

DevTools에서 GGUF 지원 모델만 표시하도록 수정:
- Qwen2.5-1.5B ✓
- Qwen2.5-3B ✓
- Gemma2-2B ✓
- Llama3-8B ✓
```

### 8.3 위기 3: 양자화 후 품질 저하

```
상황:
──────
GGUF 변환 성공
→ q4_k_m 양자화 적용
→ 응답 품질 눈에 띄게 저하
```

```
원인:
──────
q4_k_m = 4비트 양자화
→ 숫자 정밀도가 크게 낮아짐
→ LoRA로 학습한 미세한 차이가 손실됨

원본: 3.141592653589
q4:   3.1

LoRA 학습 = 미세한 가중치 변화 학습
양자화 = 그 미세한 변화를 뭉개버림
```

```
해결:
──────
LoRA 모델 테스트 시:
- q8_0 또는 f16 사용 (정밀도 유지)

배포 시:
- q4_k_m 사용 가능 (약간 품질 손실 감수)

권장:
- 작은 모델 (1.5B~3B): q8_0 사용
- 큰 모델 (7B+): q4_k_m 사용 (메모리 제약)
```

### 8.4 위기 4: Ollama 모델 목록에 안 보임

## 9. 냥체 제거 결정

### 9.1 냥체란?

```
냥체 = 문장 끝에 "냥", "냐", "야옹" 붙이기

예시:
- "배고파냥~"
- "놀자냥!"
- "싫어냥."
```

### 9.2 왜 냥체를 썼는가?

```
초기 생각:
──────────
"고양이 = 냥 붙이면 고양이답다"
→ 쉽고 명확한 규칙
→ 평가도 쉬움 (냥 있으면 +점수)
```

### 9.3 왜 냥체를 없앴는가?

```
문제 발견:
──────────
1. 문법적 부자연스러움
   - "뭐야냥" → 어색
   - "알았냥" → 어색
   - 한국어 문법에 안 맞음

2. 인위적인 느낌
   - 진짜 고양이 감정보다 "냥 붙이기"에 집중
   - 캐릭터성 저하

3. LLM이 강제로 냥 붙이려다 어색한 문장 생성
   - "그것은 좋은 생각이냥." ← 매우 어색
```

### 9.4 대안: 자연스러운 고양이다움

```
냥체 대신:
──────────
1. 행동 묘사 (괄호)
   - (골골), (하품), (꼬리 흔들며)

2. 고양이 특유 표현
   - "골골", "그르릉", "하악", "우다다"

3. 짧고 직설적인 말투
   - 고양이는 장황하게 설명 안 함

4. 츤데레/변덕스러운 태도
   - 관심 없는 척, 갑자기 애교
```

### 9.5 변경 전후 비교

```
Before (냥체):
─────────────
"(하품) 졸려냥... 귀찮냥."

After (자연스러움):
─────────────────
"(하품) 졸려... 귀찮아."

→ 더 자연스럽고 캐릭터성 유지
→ 행동 묘사 (하품)이 고양이다움 표현
```

## 10. 기술 용어 사전

### 10.1 AI/LLM 기본

| 용어 | 설명 |
|------|------|
| **LLM** | Large Language Model. 대규모 언어 모델. GPT, Llama 등 |
| **파라미터** | 모델이 학습한 숫자들. 1.5B = 15억 개 |
| **토큰** | 텍스트를 쪼갠 단위. "안녕하세요" ≈ 3~4 토큰 |
| **추론(Inference)** | 학습된 모델로 결과를 생성하는 것 |
| **프롬프트** | 모델에게 주는 입력 텍스트 |

### 10.2 LoRA 관련

| 용어 | 설명 |
|------|------|
| **LoRA** | Low-Rank Adaptation. 효율적인 미세조정 방법 |
| **Rank (R)** | LoRA 어댑터의 크기. 클수록 표현력 좋지만 무거움 |
| **Alpha** | 학습률 스케일. 보통 R의 2배 |
| **Adapter** | LoRA 학습 결과물. 수십MB 크기의 가중치 파일 |
| **Merge** | LoRA를 베이스 모델에 합치는 것 |

### 10.3 양자화 관련

| 용어 | 설명 |
|------|------|
| **양자화(Quantization)** | 숫자 정밀도 낮춰서 용량 줄이기 |
| **f16** | 16비트 부동소수점. 원본 품질 |
| **q8_0** | 8비트 양자화. 품질 좋음, 용량 50% |
| **q4_k_m** | 4비트 양자화. 용량 25%, 약간 품질 손실 |
| **GGUF** | llama.cpp용 모델 파일 형식 |

### 10.4 Ollama 관련

| 용어 | 설명 |
|------|------|
| **Modelfile** | Ollama 모델 설정 파일 |
| **FROM** | 베이스 모델/GGUF 파일 지정 |
| **SYSTEM** | 기본 시스템 프롬프트 |
| **PARAMETER** | temperature, top_p 등 설정 |

### 10.5 프로젝트 용어

| 용어 | 설명 |
|------|------|
| **Control** | 게임 상태를 JSON으로 정리한 것 |
| **TrustTier** | 신뢰도 구간 (LOW/MID/HIGH) |
| **CatScore** | 고양이다움 점수 |
| **행동 묘사** | (괄호) 안의 행동 표현 |
| **DevTools** | 개발자 도구 (WPF 앱) |

## 마무리: 핵심 교훈

```
1. 형식 통일이 중요하다
   - 학습 데이터 ↔ 벤치마크 ↔ 게임 프롬프트
   - 형식이 다르면 학습 효과 없음

2. 측정 없이 개선 없다
   - "느낌"이 아니라 "점수"로 비교
   - 벤치마크 시스템 필수

3. 작게 시작해서 검증
   - 500개 데이터로 먼저 테스트
   - 효과 확인 후 확장

4. 인위적인 규칙보다 자연스러움
   - 냥체 → 행동 묘사
   - 강제보다 자연스러운 표현

5. 도구 선택의 중요성
   - GGUF 지원 여부 확인
   - 양자화 레벨 선택 주의
```
